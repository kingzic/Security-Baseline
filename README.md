# Security Baseline and Controlled Testing

Windows Endpoint Baseline, Linux Access Control, Network Traffic Analysis, and Controlled Security Testing in an Isolated Virtual Lab.

---

## Objective

This lab establishes normal operating baselines for a Windows endpoint and a Linux host, applies role-based access control on Linux, captures and interprets routine network traffic, and then performs controlled reconnaissance and authentication testing to observe how each system logs that activity. The goal is to compare expected, everyday behaviour against the evidence generated by deliberate, authorised testing, and to draw practical security conclusions from the difference.

---

## Lab Environment

The exercise was carried out in an isolated virtual network using the following machines:

| Role | Platform | Purpose |
|---|---|---|
| Windows Endpoint | Windows 11 Pro | Baseline profiling — system info, firewall, services, ports, processes |
| Linux Host (Kali) | Kali Linux | User/group administration, access control testing, SSH logging |
| Target Host | Ubuntu | Network traffic analysis and controlled scan/brute-force target |

> Private (internal) IP addresses are used throughout this lab and are not sensitive outside the lab network. Any addresses shown below have been masked where practical.

## Linux User Administration and Access Control

On the Linux host, two standard user accounts (referred to here as **User A** and **User B**) and a dedicated group were created to demonstrate role-based access control (RBAC) and discretionary access control (DAC) enforcement, then deliberately tested to confirm the controls actually held.

### Account and Group Provisioning

```bash
sudo useradd -m -s /bin/bash userA
sudo useradd -m -s /bin/bash userB

sudo passwd userA
# New password:
# Retype new password:
# passwd: password updated successfully

sudo passwd userB
# passwd: password updated successfully

sudo groupadd SOCanalysts
sudo usermod -aG SOCanalysts userA
sudo usermod -aG SOCanalysts userB

getent group SOCanalysts
# SOCanalysts:x:1004:userA,userB
```

### Directory Permission Enforcement (`chmod 770`)

```bash
sudo mkdir -p /srv/project
sudo chown userA:SOCanalysts /srv/project
sudo chmod 770 /srv/project

ls -ld /srv/project
# drwxrwx--- 2 userA SOCanalysts 4096 Oct  8 17:14 /srv/project

sudo ls -l /srv/project
# total 4
# -rw-r----- 1 userA SOCanalysts 15 Oct  8 17:19 report.txt

sudo -u userA cat /srv/project/report.txt
# test data
```

Listing the directory and reading its file succeeded only for the authorised user, confirming the restriction was enforced at the filesystem level rather than merely configured.

### Privilege Boundary Testing

```bash
sudo gpasswd -d userB SOCanalysts
# Removing user userB from group SOCanalysts

sudo -u userB cat /srv/project/report.txt
# cat: /srv/project/report.txt: Permission denied
```

```bash
(userB)$ sudo whoami
# [sudo] password for userB:
# userB is not in the sudoers file.
```

A user removed from the authorised group was correctly denied access. A separate test confirmed a non-administrative account could not run `sudo` commands, with the attempt itself recorded in the system's authorisation log:

```
Oct 10 15:13:37 kali sudo[32757]: userB : user NOT in sudoers ; TTY=pts/0 ; PWD=/home/userB ; USER=root ; COMMAND=/usr/bin/whoami
```

## Controlled Security Testing

With the baseline established, two controlled, authorised activities were performed against the target host to observe how the resulting telemetry differs from the traffic and logs captured above.

### Port Scan (Nmap)

```bash
sudo nmap -sS -p 22,80,443,8080 <target-ip>
```

```

Nmap scan report for Ubuntu (<target-ip>)
Host is up (0.00042s latency).

PORT     STATE  SERVICE
22/tcp   open   ssh
80/tcp   closed http
443/tcp  open   https
8080/tcp open   http-proxy
MAC Address: 08:00:27:1E:BF:7C (Oracle VirtualBox virtual NIC)

Nmap done: 1 IP address (1 host up) scanned in 0.17 seconds
```

The SYN scan completed in under a second and identified SSH and HTTPS as open, HTTP as closed, and an HTTP-proxy service listening on an alternate port — a quick, low-noise picture of exposed services without establishing full connections on each port.

## Baseline vs. Controlled Activity

| Observation | Normal Baseline | Controlled Activity | Security Relevance |
|---|---|---|---|
| SSH logins | One attempt, immediately accepted | Multiple rapid failures against one account before/without success | A short burst of failed logins against one account is the classic signature of password guessing — worth investigating, though not proof of compromise on its own |
| Port exposure | Not scanned during normal use | Nmap enumerated open ports (SSH, HTTPS/proxy) in under a second | A fast, targeted scan across multiple ports with no completed sessions is a reconnaissance signature that often precedes an attack |
| Directory access | Authorised group member reads/writes freely | Same action denied once group membership was revoked | Confirms access control is enforced by the OS, not just configured on paper |
| Privileged commands | N/A | `sudo` denied for a non-privileged account, with the attempt itself logged | Shows that even failed privilege-escalation attempts leave an auditable trail |

> An unusual pattern is a reason to investigate, not a conclusion of compromise. In this lab, every "controlled activity" event is confirmed benign because it was performed intentionally and is documented above. In a live environment, the same evidence would need further correlation (source attribution, account history, concurrent alerts) before reaching a conclusion.

## Findings and Recommendations

### Findings

- Both the Windows and Linux hosts produced clear, attributable logs for authentication and account-management events, which is the foundation of any incident investigation.
- Discretionary access controls (`chmod`, group membership) on Linux were correctly enforced at the OS level, not just at the configuration level.
- A short, low-noise port scan completed before any rate-limiting or blocking occurred, showing that log review alone is not sufficient to catch reconnaissance in real time.
- Repeated failed SSH logins were fully captured in the system log, but nothing on the host automatically responded to or blocked the activity.

### Recommendations

- Deploy an automated intrusion-prevention tool (e.g. **Fail2ban**) to detect and temporarily block repeated authentication failures from the same source.
- Move toward **SSH key-based authentication** and disable password login where operationally feasible.
- Apply a **default-deny firewall policy** on exposed hosts, permitting only the ports and source addresses required.
- Forward authentication and firewall logs to a **central log-management or SIEM platform** rather than relying on manual, per-host log review.
- Periodically re-run this baseline-versus-activity comparison to confirm new controls are producing the expected telemetry.

---

## Conclusion

This lab demonstrated end-to-end security monitoring fundamentals: establishing what "normal" looks like on a Windows endpoint and a Linux host, enforcing and verifying access controls, capturing routine network traffic, and then generating controlled security events to see how each layer of the environment records them. The exercise confirmed that logging across both operating systems is detailed and reliable, but also that detection and response — recognising and acting on that evidence quickly — requires additional tooling beyond logging alone.

---

## Challenges Faced

1. **Capture permissions:** `tshark` run with `sudo` failed to write the capture file to the home directory because it drops root privileges after starting, requiring the output path to be changed to `/tmp` or `-Z none` used to retain privileges.
2. **Wrong capture interface:** Wireshark/tshark initially captured on the wrong network adapter, requiring a test ping to confirm the correct interface.
3. **DNS traffic location:** DNS queries went to the network gateway rather than the expected host, requiring the capture filter to be adjusted once the actual resolver was identified.
4. **Noise in captures:** unrelated background traffic cluttered early captures, requiring host-specific filters to isolate the relevant lab traffic.
5. **Inaccessible reference documentation:** a linked Notion page could not be scraped automatically since it requires JavaScript to render, requiring its content to be copied manually instead.
6. **Public-document review:** several screenshots contained identifying hostnames, usernames, or IPs, requiring a separate redaction and selection pass before they could be used in the shared report.
7. **Evidence coordination:** screenshots collected across multiple sessions had to be carefully matched to the correct command and section during final write-up.
